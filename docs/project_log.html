01

Build the security console

Starting point · the repository had no frontend

Why

The gateway made decisions nobody could see. A four-layer pipeline that blocks some requests, flags others and forwards the rest is impossible to reason about from a JSONL file.

How

React, TypeScript, Vite, Tailwind. Eight pages: Overview, Live Traffic, Threats, Threat Investigation, ML Intelligence, Request Logs, System Health, Configuration.

Two constraints shaped the architecture. The gateway sends no CORS headers — deliberately, it is a reverse proxy for an API, not a browser app — so the console is served same-origin with Vite proxying /__guard. And the gateway does not serve its event log over HTTP, so rather than add an endpoint just to feed a dashboard, the Vite dev server reads the file directly.

Three rules the UI holds itself to: a block is attributed to the layer the gateway recorded and never inferred from an HTTP status; "would block" is its own state, because an ML verdict under enforce-l1 is recorded but forwarded; and a metric the backend does not expose says so rather than being filled in.

Result

46 files, ~5,100 lines, committed as 042c68a. All eight routes verified in a real browser with no console errors. No backend file was touched.

Two bugs found by testing, not by reading

The log reader dropped one record per poll, because it trimmed a partial first line even when the cursor was already on a line boundary. And a chart axis clipped its leading digit, showing "600" where the value was 1600.

02

Audit whether ML should block

ZORO 1.0 · docs/ZORO_1.0.md

Why

The gateway runs GUARD_MODE=enforce-l1: signatures and rate limits block, ML verdicts are recorded only. The question was whether to promote to full enforce.

How

No theory. Ground-truth traffic through the live gateway, with labels known by construction because the harness generated them.

Result

Keep enforce-l1. ML enforcement would have blocked between 31% and 88% of legitimate traffic depending on endpoint mix. Separability measured at chance. Layer 1, by contrast, produced zero false positives while blocking 68% of attacks.

Wrong turn #1, corrected

The first report named the calibration variance as the root cause — a half-byte standard deviation on the login endpoint. Tested by intervention, that was wrong: patching it changed nothing, and a variance floor made it slightly worse. Ablating all 34 features one at a time left every false positive in place. No single feature caused it.

Wrong turn #2, corrected

The report also stated a single false-positive rate of 57.1% and an AUC of 0.479 "below chance". Both were over-precise. Re-measured across independent samples, the rate is mix-dependent (31–88%) and the AUC is simply "about 0.5". The single-draw number was an anecdote, which is exactly the error the project later set out to document.

04

Find the real cause

The finding the whole project now rests on

How

After the feature ablation came back empty, the question changed from "which feature" to "which requests". Comparing per-endpoint reconstruction error between the training corpus and live traffic gave a 1,230× ratio on /api/products and 803× on login. Then one direct test settled it.

Same endpoint, same client, same intent
RequestQuery paramsScore (threshold 0.25)Verdict
GET /api/products00.9948would block
GET /api/products?page=2&limit=2020.0003allowed
GET /api/comments00.9979would block
GET /api/comments?page=1&limit=2020.0002allowed

The model learned the generator's URL habits, not what an attack is. The traffic simulator emitted /api/products as ?page=N&limit=M on every one of 3,260 sessions and never bare, so omitting an optional parameter became more anomalous than most real attacks.

common/features.py deliberately excludes the URL to prevent exactly this — its own comment explains that the previous pipeline one-hot encoded the path and learned "path == /wp-admin means attack". The shortcut returned through q_param_count, q_total_len and q_special_ratio, which together fingerprint how each endpoint is normally called.

05

Build a way to measure honestly

Phase A · docs/BASELINE.md

Why

Every pool train.py builds — base, meta, val, test — comes from one generator. A model can score F1 0.99 on held-out data and fail on anything else, and no existing measurement could tell the difference. There is no production traffic available.

How

validate_client.py: a second traffic client written from the backend's API contract, sharing no code, no word list and no payload builder with the generator. Disjoint identity pools, different pagination conventions, different body-field subsets, independently written attacks. Independence is asserted by test, not by intention.

evaluate_live.py: replays a labelled corpus through the gateway and reports false positives overall and per endpoint, recall split into what Layer 1 already catches versus what only ML can, separability, autoencoder saturation, and latency.

Two measurement bugs, both mine, both caught

Pacing. The first run went at 6 requests/second against a 240-per-minute limit. 352 of 632 requests were rate-blocked at Layer 1, never reached the models, and silently vanished from the measurement rather than erroring.

Pairing. Matching corpus rows to log entries in order pulled in leftovers from a previous run, producing a confident "Layer 1 blocks 16.67% of legitimate traffic" for requests Layer 1 had never touched. The client now stamps its send window into the manifest.

Both produced plausible-looking numbers. That is the argument for anchoring a measurement rather than eyeballing it.

06

Fix the training data, not the model

Phase B · the intervention experiment

How

  • B1–B4. Every endpoint emitting one canonical shape was widened. /api/products went from 1 query shape to 20; /api/orders from always-bare to 8; POST bodies from always-complete to 4–6 field combinations. A deliberate bare-call branch replaced relying on four independent coin flips, which produced the bare shape only 12 times in 3,260 requests. All three session profiles — 42% of generated sessions — were routed through the same helpers instead of emitting literal strings.
  • B5. Per-endpoint score normalisation. Normal reconstruction error spans three orders of magnitude between endpoints, so one global ceiling saturates some completely — and a saturated score gives benign and hostile requests the identical value. Same baseline-relative construction as body_size_z, so FEATURE_NAMES is untouched.

Result

Changing only the training data, with no change to the model, features, architecture or hyperparameters:

ModelFalse positivesPrecisionF1ROC-AUCAE saturation
Shipped44.49%0.2870.44610.732032.9%
After widening13.58%0.5370.66670.835811.8%
The counter-intuitive result

Recall fell, and it is not a regression. The shipped model's apparent 100% recall was a blanket endpoint flag — the same phenomenon producing its 44% false positives. Removing the blanket removed both. The two numbers were never independent, and the detections that vanished were never discriminative.

The sharpest evidence: a NoSQL injection against /api/users/login scores 0.436 while a genuine login scores 0.936. The attack looks more normal than real traffic, so no threshold can separate them — they are ordered the wrong way round.

07

Make the failure impossible to repeat

Phase C · guards, not warnings
  • C1. tests/test_generate.py, 15 tests asserting distributional properties of the generator: every endpoint in ≥3 query shapes, the bare form at ≥5% of traffic, POST bodies varying, unusual HTTP methods exercised, and normal traffic never tripping a BLOCK rule. Verified it can actually fail by neutering the variation helpers.
  • C2. The zero-variance warning became a hard abort. It had printed on every run for months and been read past every time, while costing two measured regressions. A warning nobody acts on is not a control.
  • C3. Normalisation bounds moved from in-sample to out-of-sample. They were percentiles of the exact rows the autoencoder was fitted on — the same mistake as reporting accuracy on training data. The resulting ceiling sat at the 52nd percentile of real traffic, flattening half of all legitimate requests to the score every attack gets.
  • C4. calibrate.py now re-derives those bounds, globally and per endpoint, from the deployment's own traffic. It previously reused them from decision.json, so a new backend inherited the training corpus's scale.
08

Choose the model on repeated draws

Phase D · rule fixed before the numbers were seen

Why fix the rule first

Choosing the criterion after seeing the results is cherry-picking. The rule: decide on cross-generator performance, treating in-distribution numbers as diagnostic only; rank by ROC-AUC because it is threshold-independent; break ties on recall at the project's own 1% budget; and judge on four draws, not one.

Four independent client draws

The shipped model is far worse than any single draw suggested. On one draw its ROC-AUC fell to 0.3888 — below chance, ranking attacks below legitimate traffic. The earlier 44.49% was the optimistic end of its range.

The tie-break was decisive. At a 1% false-positive budget, models_b3 catches 0.5% of attacks and models_b4 catches 13.4%.

Wrong turn #3, corrected

Predicted that the weaker gate-passing model underperformed because its corpus was half-size. Generated a full-size one — 20,654 normal rows against 14,849 — and it was still weaker. Corpus size was not the explanation; the extra coverage fixes genuinely cost detection, because teaching the model that bulk quantities and unusual methods are normal also teaches it that attacks resembling them are normal.

09

Make ML blocking safe to switch on

Phase E · verified live

Why

Detection is a property of the model; enforcement is a property of the deployment. They were the same boolean, which made turning ML blocking on all-or-nothing with no reverse gear.

  • E0. Admin authentication. /__guard/* sat on the only published port with none. A safety brake anyone on the network can clear is worse than no brake, because an operator believes they are protected.
  • E1. Separate detection and enforcement thresholds, a per-endpoint allowlist, and a canary percentage. One knob carries "never" — the percentage — because two never-defaults create the failure where an operator sets one, sees nothing, and loosens both.
  • E3. Deterministic canary buckets, so a client never flaps and ramping only ever adds clients.
  • E4. An automatic brake measuring the would-block rate across everything that reached the models — so the figure is meaningful at 0% rollout, which is how you learn whether enforcement is safe before anyone gets a 403. A minimum distinct-client count means one attacker can never trip it alone.
  • E5–E6. enforce_gate on every event, an ml block in health and stats, and all of it surfaced on the console.
defaults        mode=enforce-l1  enforcing_ml=False  rollout=0%   identical to before
enforcement on  /api/products  403  layer=L4-meta  gate='enforce'
                /api/comments  200  layer=L4-meta  gate='endpoint-not-enabled'
                /.env          403  layer=L1-rules gate='l1'      L1 unaffected
brake engaged   /api/products  200  ML stops, L1 keeps blocking, status=degraded
after reset     enforcing_ml=True, status=healthy

A unit test caught that resetting the brake would immediately re-engage, because the stale window still exceeded the ceiling. reset() now clears the measurement window too.

10

An expressivity limit, not a data problem

docs/feature_case.html

Three attack families are invisible to the detector and retraining cannot fix it. The 34 features measure shape — length, depth, entropy, parameter count. Shape is not where these attacks live.

FamilyWhat makes it hostileCandidate featureAUC99th pct benign
massassignextra field namesbody_unknown_field_ratio1.0000.0000
nosqlan object where a string belongs — a typebody_nonscalar_ratio1.0000.0000
enuma huge parameter valuemax_numeric_magnitude1.0006.22

Each blind family is separated perfectly by a single feature, and a different one each time — what an expressive gap looks like rather than a statistical one. Three of the four candidates read exactly zero at the 99th percentile of legitimate traffic.

Adding them breaks the feature contract and forces a coordinated retrain, so it is a decision rather than something to slip in.

11

Reframe the paper

manuscript/REFRAME_PLAN.md · IEEE conference

The existing manuscript's abstract already ended with "flagging a transfer risk that recall-only reporting hides." That was a caveat. It is now a measurement, and it is the most novel thing this project has produced.

New framing: single-generator evaluation systematically overstates learned API anomaly detection. The system becomes the instrument; the finding becomes the paper. Nothing is discarded — the session-grouped splits, withheld families and FPR budget are what make the result credible, because the in-distribution number was obtained under stricter discipline than the literature usually applies and still failed to transfer.

Still needed: a confidence interval on the transfer gap, McNemar for the new model, and three figures.

Two decisions are yours.

The model. models_b4 measures best on independent traffic but its corpus fails the C2 variance gate written in this same project. The gate-passing alternative is weaker. I will not weaken a security control to make a preferred model pass, nor ship a model the project's own quality control rejects without saying so.

The commits. Everything except the console is uncommitted. The three gateway defect fixes stand on their own merit, independent of any ML argument, and are the most valuable thing here.

On the false positives, since it is the obvious worry

In the live demo the gateway handled 2,324 requests: 2,029 allowed, 295 blocked by signature rules, 1,877 ML detections recorded and zero enforced.

That last pair is not a failure. It is the architecture working. A bad model raised 1,877 verdicts and the layered design acted on none of them, so 2,029 legitimate requests went through untouched. A project that reports F1 0.99 and stops is one that did not look outside its own generator. This one looked, measured the gap, found the mechanism, and fixed most of it by intervention.
