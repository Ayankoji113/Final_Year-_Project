MicroAPI Guard · Feature-set decision · 2026-09-12

The Fourteen Unseeable Attacks

Three attack families are invisible to the detector, and no amount of retraining will change that. They carry no anomalous shape. The 34 features cannot express what makes them hostile.

Decision change FEATURE_NAMES, or accept the gap Evidence 508 benign + 91 attacks, independent client Status awaiting approval
What I am asking for

Permission to add four features and retrain

The plan we agreed says keep the 34-feature contract and fix the data instead. That was the right call and it worked: false positives fell from 44.5% to 8.5%. But the measurement that followed shows three attack families cannot be detected by any model built on these 34 features, because the features do not encode the thing that makes those requests attacks.

I tested four candidate features against the same corpus before proposing them. Three of them separate a family perfectly, and two cost nothing in false positives.

Reading that as "B2 traded recall for precision" is the obvious interpretation and it is wrong. The two numbers were never independent.

The shipped model scored 100% recall because it flagged everything on those endpoints. That same blanket is what produced 44% false positives. Removing the blanket removed both. The detections that vanished were never discriminative — they were a stopped clock being right twice a day.

The result that settles it

Under B2, a NoSQL injection against /api/users/login scores 0.436. A genuine login on the same endpoint scores 0.936. The attack looks more normal than real traffic does. No threshold placed anywhere separates them, because they are the wrong way round.

The feature set measures shape: how long, how deep, how much entropy, how many parameters. That was a deliberate and correct decision — it is what makes the detector work in front of any backend without learning one API’s vocabulary.

But a mass-assignment attack is the same length as a real registration. An enumeration probe has the same parameter count as real pagination. A NoSQL payload has the same field names as a real login. Shape is simply not where the signal is.

Each of the three blind families is separated perfectly by a single feature, and it is a different feature each time. That is what you would expect if the gap is expressive rather than statistical: nothing is missing from the model, something is missing from its vocabulary.

Three of the four are exactly zero across every legitimate request measured. Real clients do not send unknown field names, do not nest objects where scalars belong, and do not send negative quantities. The fourth needs care: log1p of about 500 is ordinary pagination, so it is a graded feature rather than a flag.

What it costs, and the one real risk

Nothing here is free

The feature contract breaks. detector.load() refuses any model whose feature_names differ from the running build, so the gateway will not start until it is retrained and the artefacts are replaced. That guard is doing its job; it just means this is a coordinated change, not a hot reload.

Everything downstream retrains. The corpus must be regenerated so the new features are exercised, then train.py, tune.py on seeds 11–15 and validate.py on seeds 1–10, and compare.py must mirror the change.

The risk worth arguing about

body_unknown_field_ratio needs to know which fields an endpoint legitimately accepts, and that is one step from learning the backend’s vocabulary — the exact failure features.py was rewritten to eliminate.

It survives on a distinction the codebase already relies on: the feature is how much of this body is unfamiliar for this endpoint, learned from the calibration baseline, not which endpoint this is. That is the same construction as body_size_z and path_known. The check is that the two backend-agnosticism tests in test_features.py still pass afterwards — if they fail, the feature is wrong and should be dropped rather than argued for.

Recommendation

Adopt B1 now. Approve the four features as a separate, measured change.

B1 is the best model this project has produced: F1 0.6667 against the shipped 0.4461, ROC-AUC 0.8395 against 0.7320, false positives down from 44.5% to 13.6%, and six of seven attack families still at 100%. It beats what is deployed on every axis that matters. Ship it into enforce-l1 where it changes nothing about blocking but improves everything the dashboard reports.

Then take the feature change deliberately, with the same measurement discipline: regenerate, retrain, re-measure against the independent client, and keep it only if the blind families move and the backend-agnosticism tests hold.

The alternative is to accept permanently that mass assignment, NoSQL injection and enumeration are undetectable by this system. That is a defensible engineering position. It is not a defensible silent position, which is why this is a decision rather than a commit.

Evidence: 622 requests from an independent client sharing no code with the training generator; three model generations scored on identical traffic; candidate features computed from retained raw bodies, which the event log deliberately does not store.
